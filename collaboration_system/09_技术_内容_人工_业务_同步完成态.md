# 技术、内容、人工、业务与同步完成态

## 解决什么问题

这个机制防止“绿色测试”“本地文件”“commit 成功”被写成用户接受、专业批准或业务成立。每次汇报都必须说明完成的是哪一层，哪些仍是待验证。

## 什么时候触发

- 最终回报。
- 日志和 project_facts 更新。
- Project 包生成。
- 用户质疑“这算完成吗”。
- 任何医疗、合规、外部动作或业务结果被提及。

## 五层完成态

| 层 | 证明什么 | 不证明什么 | 证据例子 |
| --- | --- | --- | --- |
| technical_validation | 文件、格式、测试、命令或结构通过 | 内容正确、用户接受、业务成立 | unit test、link check、git diff check |
| content_validation | 内容与已锁定目标、边界、事实分类一致 | 用户已验收、市场成立 | 人工/模型复审、对照执行单 |
| human_review | 用户或专业主体已经复审并接受 | 自动化长期稳定、业务结果 | 用户明确确认、医生/律师/合规书面意见 |
| business_observation | 有真实、合规的交易、履约、客户反馈或外部证据 | 长期可复制或已规模化 | 付款、到院、签约、合规记录 |
| sync_status | commit、push、remote readback、Project 包路径 | 以上任何业务层结果 | SHA、origin/main、manifest |

## 状态词

使用 `已确认`、`部分成立`、`待验证`、`推测`、`blocked`、`continue`、`superseded`。每个状态后必须有证据或缺口。

## 完成态判断流程

1. 列出本轮 Done When。
2. 按五层分别写 evidence。
3. 任何未验证层保持 `待验证`。
4. 若缺关键层，状态为 continue 或 blocked，不写 completed。
5. 若需要用户、人审或专业主体，不得由 Codex 替代。

## 医疗项目红线

技术上创建了价格表，不证明价格可报价；公开资料里出现医院项目，不证明医院合作；研究报告显示需求，不证明客户愿意付费；问卷/聊天有兴趣，不证明订单；AI 写了风险边界，不证明法律或医疗合规已完成。

## 反例

- “Project 包生成了”被写成“Project 已更新”。正确：package_generated=true；user_uploaded_to_project_ui=unknown；project_ui_verified=unknown。
- “测试通过”被写成“协作机制已在真实项目长期验证”。正确：technical_validation 已确认；长期效果待真实任务观察。
- “候选供应商表完成”被写成“供应商已确认”。正确：Fact candidate，不是 Confirmed fact。
